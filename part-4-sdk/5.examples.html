4.5 Simulation and Hardware Use¶

Simulation Integration¶

Terminal 1:

bash scripts/start_mujoco.sh --config config_sim.yaml

Terminal 2:

export YOBOTICS_LCM_URL='udpm://239.255.76.67:7667?ttl=255'
yobotics_sdk/build/yobot_robot_state_client

Terminal 3:

yobotics_sdk/build/yobot_sport_client

Confirm state reading first, then switch from DAMP to standing and low-speed walking.

Hardware Integration¶

  1. Start the controller according to Part 3 and confirm the robot is safely supported.
  2. Configure the SDK host and robot with the same LCM multicast URL.
  3. Use the state example to confirm bidirectional networking.
  4. Start the motion example and validate from DAMP and RECOVERY_STAND.

In multi-interface environments, make sure multicast routing points to the robot network interface. You can first run bash scripts/monitor_lcm.sh --no-gui to determine whether the issue is in the network or the SDK.

Integration Success Indicators¶

  1. The state client works before the motion client and shows continuous updates.
  2. QUAD_ROBOT_CONTROL_Y20W appears after SDK publishing.
  3. Mode changes are confirmed in QUAD_ROBOT_STATE_Y20W.
  4. Small velocity commands move in the correct direction, and the robot stops after zeroing.
  5. The client sends zero velocity and switches back to a safe mode before exit.

Common Issues¶

Symptom Handling
SDK starts normally but has no state Compare SDK and controller LCM URLs; check multicast interface
State is normal but mode does not change Check continuous EnableLCMControl() and whether another input source overrides it
Mode changes but there is no motion Confirm the mode allows motion, velocity is nonzero, and there are no faults
Robot keeps moving after key release Confirm the business loop actively sends zero velocity and does not rely on process exit
Multiple clients overwrite each other Keep one control publisher; make other clients read-only
