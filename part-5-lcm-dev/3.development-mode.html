5.3 DEVELOPMENT Mode¶

DEVELOPMENT mode lets an independent Python process read robot state prepared by the controller and continuously submit 16D wheel-leg commands. It is a runtime mode in the controller state machine, not a synonym for “the algorithm process has started”.

Five Different Stages¶

Stage What it proves What it does not prove
Algorithm process started Python, configuration, and dependencies are basically usable Controller is online or LCM is reachable
Development state received State channel, types, and robot_id are usable Controller has accepted external commands
Enable command published Command channel has a sender Controller has switched mode
mode in state changed Controller state machine has responded Joint order and action direction are correct
Joint state follows target The full control chain has started working Motion is stable long-term or suitable for hardware

Debugging must confirm each stage in order. Do not infer that the robot is controlled by the algorithm just because the command channel is visible.

Recommended Lifecycle¶

Start controller
  -> DEVELOPMENT state publishes continuously
  -> start algorithm and validate config/model
  -> warmup completes
  -> algorithm sends enable=1
  -> controller enters DEVELOPMENT
  -> inference thread updates command cache
  -> send thread continuously publishes cached commands
  -> end requested or safety stop triggered
  -> send enable=0 zero command for about 100 ms
  -> controller returns to DAMP or another safe mode

AlgorithmBase Initialization Order¶

  1. Parse --config and read YAML.
  2. Create LCMInterface and subscribe to lcm.state_channel.
  3. Initialize model_params and convert list parameters to NumPy arrays.
  4. Call subclass _load_policy(); walk loads ONNX, wave skips the model.
  5. Start the LCM interface so warmup can receive real state.
  6. Create a zero action_buffer.
  7. Run warmup according to warmup_count.
  8. Read execution frequency, send frequency, auto-start/end, and maximum runtime.
  9. run() starts the inference thread and LCM send thread.

Configuration paths are resolved relative to the algorithm script or current working directory. Passing a complete relative path from the project root is recommended for reproducibility.

Two Parallel Loops¶

Inference Loop¶

The inference loop runs at execution.frequency:

  1. Read the latest state cache.
  2. Confirm local development_mode_active.
  3. Call compute_observation(state).
  4. Reject observations containing NaN/Inf.
  5. Call _run_inference(obs).
  6. Reject actions containing NaN/Inf.
  7. Update action_buffer under lock.
  8. Call process_action() to update the latest command cache.

Send Loop¶

The send loop runs at execution.lcm_send_frequency. It repeatedly publishes the latest complete command so the controller does not depend on a slower model-inference frequency. For example, walk defaults to 50 Hz inference and 500 Hz sending.

action_buffer_lock protects historical actions, latest_command_lock protects commands waiting to be sent, and state_lock protects runtime state. Custom algorithms should use the same locks when updating these shared objects.

Frequencies are not real-time guarantees

The current implementation uses Python threads and time.sleep() scheduling. Configured values are target frequencies, not hard real-time guarantees. CPU load, inference time, and debug printing all affect actual frequency; measure it with LCM monitoring.

Key Configuration¶

Field Type Current examples Behavior
execution.frequency Hz walk 50, wave 100 Observation, inference, or rule-computation cycle
execution.lcm_send_frequency Hz walk 500, wave 200 Repeat-send cycle for the latest command
execution.auto_start bool true Locally activates development flow after matching state is received
execution.auto_end bool true Calls the end flow when maximum runtime is reached
execution.max_execution_time seconds 0 0 means no time-based auto end
policy.warmup_count count walk 500, wave 0 Uses real state for model warmup
policy.action_threshold action value walk 100, wave 200 Reports actions with absolute value above the threshold during warmup

auto_start only changes the internal state of the algorithm process and starts sending enable commands. Whether the controller actually enters DEVELOPMENT is still decided by the controller.

Warmup Behavior¶

Walk warmup needs the actor, encoder, and real state:

  • Each attempt waits up to about 5 seconds for state.
  • After state is received, it constructs an observation and runs one inference.
  • It records action indices whose absolute value exceeds action_threshold.
  • At the end of warmup, if the last recorded abnormal actions still exist, the program exits with an error.
  • Warmup is skipped when warmup_count <= 0, the model is empty, or the encoder is empty.

Warmup helps find model loading, dimension, and obvious action-abnormality issues. It does not replace simulation stability testing or actual joint-limit checks.

Subclass Extension Points¶

Method Must care? Input/output Responsibility
_load_policy() Rule algorithms should override No fixed return Load model or explicitly set no model
compute_observation(state) Required state -> NumPy vector Reorder, scale, and construct algorithm input
_run_inference(obs) Override for special models or rules observation -> action Run ONNX or rule computation
process_action(state, action) Required state and action -> command cache Validate action and generate q/qd/tau/Kp/Kd
on_development_mode_start() Recommended none Reset counters, history, and trajectory time
on_development_mode_end() Recommended none Clean algorithm state and avoid leaving valid commands behind

Minimal Rule-Algorithm Template¶

import numpy as np
from algorithm_base import AlgorithmBase


class MyAlgorithm(AlgorithmBase):
    def _load_policy(self):
        self.model = None
        self.encoder = None
        self.policy_type = "none"

    def compute_observation(self, state):
        return np.asarray(state.rpy, dtype=np.float32)

    def _run_inference(self, obs):
        return np.zeros(16, dtype=np.float32)

    def process_action(self, state, action):
        if action is None or len(action) != 16:
            return
        if not np.all(np.isfinite(action)):
            return

        with self.latest_command_lock:
            self.latest_command = {
                "enable_development_mode": True,
                "joint_positions": self.model_params["default_joint_pos"] + action,
                "joint_velocities": np.zeros(16, dtype=np.float32),
                "joint_torques": np.zeros(16, dtype=np.float32),
                "joint_kp": self.model_params["joint_stiffness"],
                "joint_kd": self.model_params["joint_damping"],
            }

The 16D arrays in the template use the per-leg [hip, thigh, calf, wheel] order. LCMInterface splits them into 12+4 when sending.

Normal Startup¶

  1. Start simulation according to MuJoCo Startup, or start the controller according to Hardware Startup.
  2. Confirm Y20W_development_state updates continuously.
  3. Start the algorithm and wait for configuration, model, and warmup to complete.
  4. Confirm Y20W_development_command appears and robot_id=Y20W.
  5. Enter DEVELOPMENT through the gamepad or current control entry.
  6. Watch state mode, joint response, and command frequency.

Normal Stop¶

Prefer switching the controller back to DAMP or another safe mode before ending the algorithm. When using Ctrl+C, the framework runs the end flow and continuously sends disable commands for about 100 ms according to the send frequency.

Switch back to safe mode -> confirm motion stopped -> Ctrl+C -> confirm command enable=0 -> stop controller

Do not only close the terminal

Closing the algorithm process does not mean the controller has exited DEVELOPMENT. On hardware, observe the state machine and robot response to confirm a safe mode has been reached.

Exception Boundaries¶

Exception Current framework behavior Validation developers should add
No state received Warmup waits per attempt; success count may be 0 Actively check channel frequency and state freshness before startup
Observation NaN/Inf Skips that inference Find the sensor or normalization source; do not rely on skipping long-term
Inference exception Prints error and returns None Monitor consecutive failures and trigger safe exit if needed
Action NaN/Inf Skips or walk tries the previous action Verify the old action is still safe; do not hold it indefinitely
Action above threshold Recorded during warmup and may exit Runtime still needs custom limiting and joint constraints
Inference too slow Actual inference frequency drops Measure time and validate command-cache expiry strategy
Algorithm-thread exception Prints stack and continues loop Before hardware tests, verify exceptions make the controller enter a safe state

The current framework does not automatically trigger local shutdown based on last_state_time. Hardware algorithms should treat “state freshness” and “consecutive inference failures” as required failure scenarios before deployment.
