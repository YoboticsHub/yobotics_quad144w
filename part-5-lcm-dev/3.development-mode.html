5.3 DEVELOPMENT 模式¶

DEVELOPMENT 模式让独立 Python 进程读取控制器整理后的机器人状态，并持续提交 16 维轮足命令。它是控制器状态机中的一种运行模式，不是“算法进程启动”的同义词。

五个不同阶段¶

阶段 能说明什么 不能说明什么
算法进程已启动 Python、配置和依赖基本可用 控制器在线或 LCM 可达
已收到 development 状态 状态通道、类型和 robot_id 可用 控制器已接受外部命令
已发布使能命令 命令通道有发送方 控制器已切换模式
状态中的 mode 已变化 控制器状态机已响应 关节顺序和动作方向正确
关节状态跟随目标 完整控制链路开始工作 动作长期稳定或适合实机

调试时必须逐级确认，不能从“看到了命令通道”直接推断机器人已由算法控制。

推荐生命周期¶

启动控制器
  -> DEVELOPMENT 状态持续发布
  -> 启动算法并校验配置/模型
  -> 预热完成
  -> 算法发送 enable=1
  -> 控制器进入 DEVELOPMENT
  -> 推理线程更新命令缓存
  -> 发送线程持续发布缓存命令
  -> 请求结束或触发安全停止
  -> 连续发送约 100 ms 的 enable=0 清零命令
  -> 控制器回到 DAMP 等安全模式

AlgorithmBase 初始化顺序¶

  1. 解析 --config 路径并读取 YAML。
  2. 创建 LCMInterface，订阅 lcm.state_channel。
  3. 初始化 model_params，把列表参数转换为 NumPy 数组。
  4. 调用子类的 _load_policy()；walk 加载 ONNX，wave 跳过模型。
  5. 启动 LCM 接口，使预热阶段能够接收真实状态。
  6. 创建全零 action_buffer。
  7. 根据 warmup_count 执行预热。
  8. 读取执行频率、发送频率、自动开始/结束和最长运行时间。
  9. run() 启动推理线程和 LCM 发送线程。

配置路径相对算法脚本或当前工作目录解析。推荐始终从项目根目录传入完整相对路径，便于复现。

两个并行循环¶

推理循环¶

推理循环按 execution.frequency 运行：

  1. 读取最新状态缓存；
  2. 确认本地 development_mode_active；
  3. 调用 compute_observation(state)；
  4. 拒绝包含 NaN/Inf 的观测；
  5. 调用 _run_inference(obs)；
  6. 拒绝包含 NaN/Inf 的动作；
  7. 在锁保护下更新 action_buffer；
  8. 调用 process_action() 更新最新命令缓存。

发送循环¶

发送循环按 execution.lcm_send_frequency 运行。它重复发布最近一次完整命令，使控制器不依赖较慢的模型推理频率。例如 walk 默认 50 Hz 推理、500 Hz 发送。

action_buffer_lock 保护历史动作，latest_command_lock 保护待发送命令，state_lock 保护运行状态。自定义算法更新这些共享对象时应沿用相同锁。

频率并非实时保证

当前实现使用 Python 线程和 time.sleep() 调度。配置值是目标频率，不是硬实时承诺。CPU 负载、推理时间和调试打印都会影响实际频率，应通过 LCM 监控测量。

关键配置¶

字段 类型 当前示例 行为
execution.frequency Hz walk 50，wave 100 观测、推理或规则计算周期
execution.lcm_send_frequency Hz walk 500，wave 200 最近命令的重复发送周期
execution.auto_start bool true 收到匹配状态后，在算法本地激活开发流程
execution.auto_end bool true 达到最长运行时间时调用结束流程
execution.max_execution_time 秒 0 0 表示不按时间自动结束
policy.warmup_count 次 walk 500，wave 0 使用真实状态执行模型预热
policy.action_threshold 动作值 walk 100，wave 200 预热时报告绝对值越界的动作

auto_start 只改变算法进程内部状态并开始发送使能命令。是否真正进入 DEVELOPMENT 仍由控制器决定。

预热行为¶

walk 的预热需要 actor、encoder 和真实状态：

  • 每次最多等待约 5 秒获取状态；
  • 收到状态后构造观测并执行一次推理；
  • 记录动作绝对值超过 action_threshold 的索引；
  • 预热结束时若最后记录的异常仍存在，程序以错误状态退出；
  • warmup_count <= 0、模型为空或 encoder 为空时跳过预热。

预热用于发现模型加载、维度和明显动作异常，不替代仿真稳定性测试，也不检查实际关节限位。

子类扩展接口¶

方法 是否必须关注 输入/输出 责任
_load_policy() 规则算法需要覆盖 无固定返回 加载模型，或明确设置为无模型
compute_observation(state) 必须 状态 -> NumPy 向量 重排、缩放并构造算法输入
_run_inference(obs) 特殊模型或规则算法覆盖 观测 -> 动作 执行 ONNX 或规则计算
process_action(state, action) 必须 状态和动作 -> 命令缓存 校验动作，生成 q/qd/tau/Kp/Kd
on_development_mode_start() 推荐 无 重置计数器、历史和轨迹时间
on_development_mode_end() 推荐 无 清理算法状态，不直接遗留有效命令

最小规则算法模板¶

import numpy as np
from algorithm_base import AlgorithmBase


class MyAlgorithm(AlgorithmBase):
    def _load_policy(self):
        self.model = None
        self.encoder = None
        self.policy_type = "none"

    def compute_observation(self, state):
        return np.asarray(state.rpy, dtype=np.float32)

    def _run_inference(self, obs):
        return np.zeros(16, dtype=np.float32)

    def process_action(self, state, action):
        if action is None or len(action) != 16:
            return
        if not np.all(np.isfinite(action)):
            return

        with self.latest_command_lock:
            self.latest_command = {
                "enable_development_mode": True,
                "joint_positions": self.model_params["default_joint_pos"] + action,
                "joint_velocities": np.zeros(16, dtype=np.float32),
                "joint_torques": np.zeros(16, dtype=np.float32),
                "joint_kp": self.model_params["joint_stiffness"],
                "joint_kd": self.model_params["joint_damping"],
            }

模板中的 16 维数组使用每腿 [hip, thigh, calf, wheel] 顺序。LCMInterface 在发送时拆成 12+4。

正常启动¶

  1. 按 MuJoCo 启动说明启动仿真或按 实机启动说明启动控制器。
  2. 确认 Y20W_development_state 持续更新。
  3. 启动算法并等待配置、模型和预热完成。
  4. 确认 Y20W_development_command 出现且 robot_id=Y20W。
  5. 通过手柄或当前控制入口进入 DEVELOPMENT。
  6. 查看状态 mode、关节响应和命令频率。

正常停止¶

优先将控制器切回 DAMP 或其他安全模式，再结束算法。使用 Ctrl+C 时，框架会执行结束流程，并按发送频率持续发送约 100 ms 的禁用命令。

切回安全模式 -> 确认运动停止 -> Ctrl+C -> 确认命令 enable=0 -> 停止控制器

不要只关闭终端

关闭算法进程不等于控制器已经退出 DEVELOPMENT。实机上必须观察状态机和机器人响应，确认已经进入安全模式。

异常处理边界¶

异常 当前框架行为 开发者应补充的验证
一直收不到状态 预热尝试等待，成功次数可能为 0 启动前主动检查通道频率和状态新鲜度
观测 NaN/Inf 跳过当次推理 查明传感器或归一化来源，不应长期依赖跳过
推理异常 打印错误并返回 None 监控连续失败次数，必要时触发安全退出
动作 NaN/Inf 跳过或由 walk 尝试上一动作 验证旧动作仍安全，不能无限保持
动作超阈值 预热阶段记录并可能退出 运行阶段仍需自定义限幅和关节限制
推理耗时过长 实际推理频率下降 测量耗时并验证命令缓存过期策略
算法线程异常 打印堆栈并继续循环 实机测试前验证异常能让控制器进入安全状态

当前框架没有在本地根据 last_state_time 自动触发状态超时停机。实机算法应把“状态新鲜度”和“连续推理失败次数”作为上线前必须验证的失效场景。
