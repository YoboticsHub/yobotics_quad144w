5.2 16D Message Protocol¶

Y20W has 12 leg joints and 4 wheel joints. Algorithms usually use a 16D vector arranged continuously per leg, while the LCM protocol splits it into a 12D main array and a 4D supplement array.

Joint Indices¶

Algorithms use the following interleaved order:

Algorithm index Leg Joint Main-array index supplement index
0 LF hip 0 -
1 LF thigh 1 -
2 LF calf 2 -
3 LF wheel - 0
4 RF hip 3 -
5 RF thigh 4 -
6 RF calf 5 -
7 RF wheel - 1
8 LR hip 6 -
9 LR thigh 7 -
10 LR calf 8 -
11 LR wheel - 2
12 RR hip 9 -
13 RR thigh 10 -
14 RR calf 11 -
15 RR wheel - 3 
Algorithm 16D:
[LF_hip, LF_thigh, LF_calf, LF_wheel,
 RF_hip, RF_thigh, RF_calf, RF_wheel,
 LR_hip, LR_thigh, LR_calf, LR_wheel,
 RR_hip, RR_thigh, RR_calf, RR_wheel]

LCM main array:
[LF_hip, LF_thigh, LF_calf,
 RF_hip, RF_thigh, RF_calf,
 LR_hip, LR_thigh, LR_calf,
 RR_hip, RR_thigh, RR_calf]

LCM supplement:
[LF_wheel, RF_wheel, LR_wheel, RR_wheel]

The two 16D layouts are not interchangeable

The algorithm vector is interleaved with four items per leg; the serialized LCM message is a 12-item main array plus 4 supplement items. Even when the length is 16, an incorrect order can send wheel commands to leg joints.

development_state_t¶

The controller publishes through Y20W_development_state:

Field Type/length Meaning
robot_id string Robot identifier publishing the state; should currently be Y20W
joint_q float[12] 12 leg-joint positions
joint_q_supplement float[4] 4 wheel-joint positions
joint_qd float[12] 12 leg-joint velocities
joint_qd_supplement float[4] 4 wheel-joint velocities
joint_tau float[12] 12 leg-joint torques
joint_tau_supplement float[4] 4 wheel-joint torques
quat float[4] Body quaternion; the walk example uses [w, x, y, z]
rpy float[3] roll, pitch, yaw
omega float[3] Body angular velocity
acc float[3] Body acceleration
v_des float[3] Desired linear velocity; walk uses the first two values
omega_des float[3] Desired angular velocity; walk uses the z component
mode int32_t Current controller mode number

development_state_t does not contain temperature, joint faults, leg enable flags, or SPI driver state. Subscribe separately to quad_joint_state_t on Y20W_QUAD_JOINT_STATE when those are needed.

development_command_t¶

External algorithms publish through Y20W_development_command:

Field Type/length Meaning
robot_id string Target robot identifier; must be Y20W
enable_development_mode int32_t 1 requests enable, 0 requests end and zero command
joint_des_q / _supplement float[12] / float[4] Desired position
joint_des_qd / _supplement float[12] / float[4] Desired velocity
joint_des_tau / _supplement float[12] / float[4] Feedforward desired torque
joint_des_kp / _supplement float[12] / float[4] Position-error gain
joint_des_kd / _supplement float[12] / float[4] Velocity-error gain

A typical actuator target can be understood as:

tau_cmd = tau_des + kp * (q_des - q) + kd * (qd_des - qd)

This expression explains the field roles. Final limiting and execution behavior are implemented by the controller and drivers. Wheel joints are often used for velocity control, but the protocol still provides position, velocity, torque, Kp, and Kd; set them according to the current control strategy instead of guessing units or mode from the wheel name alone.

Raw Joint State¶

In addition to 12+4 position, velocity, and torque, quad_joint_state_t contains:

Field Meaning
flags[4] State flags for each leg
spi_driver_status Overall SPI driver state
joint_fault[12] / _supplement[4] Leg-joint and wheel-joint faults
joint_temp[12] / _supplement[4] Leg-joint and wheel-joint temperatures

Hardware safety monitoring should observe both DEVELOPMENT state and raw joint state. Subscribing only to development state cannot determine temperature or driver faults.

Python Recomposition Example¶

def interleave_y20w(main, wheel):
    values = []
    for leg in range(4):
        base = leg * 3
        values.extend(main[base:base + 3])
        values.append(wheel[leg])
    return values

dof_q = interleave_y20w(msg.joint_q, msg.joint_q_supplement)
dof_qd = interleave_y20w(msg.joint_qd, msg.joint_qd_supplement)
assert len(dof_q) == 16
assert len(dof_qd) == 16

Send interleaved 16D commands with the project wrapper:

command = {
    "enable_development_mode": True,
    "joint_positions": q_des_16,
    "joint_velocities": qd_des_16,
    "joint_torques": tau_des_16,
    "joint_kp": kp_16,
    "joint_kd": kd_16,
}

with algorithm.latest_command_lock:
    algorithm.latest_command = command

LCMInterface.send_command() splits inputs of exactly length 16 as four leg blocks. You can also pass explicit 12D main arrays and matching *_supplement parameters.

C++ Recomposition Example¶

#include <array>

std::array<float, 16> interleaveY20W(
    const float main_joint[12], const float wheel[4]) {
  std::array<float, 16> result{};
  for (int leg = 0; leg < 4; ++leg) {
    result[leg * 4 + 0] = main_joint[leg * 3 + 0];
    result[leg * 4 + 1] = main_joint[leg * 3 + 1];
    result[leg * 4 + 2] = main_joint[leg * 3 + 2];
    result[leg * 4 + 3] = wheel[leg];
  }
  return result;
}

When publishing C++ messages, fill joint_des_q and joint_des_q_supplement field by field. Use the same split method for velocity, torque, Kp, and Kd, and set robot_id to Y20W.

LCMInterface Input Rules¶

Input form Interpretation
None Main array and supplement are all zero
Fewer than 12 items Provided main-array values are kept; remaining main array and supplement are zero-filled
12 items 12 main joints; 4 wheel joints are zero-filled
Exactly 16 items Interpreted as four [hip, thigh, calf, wheel] leg blocks
More than 16 items First 12 items are main array, next 4 are supplement, extras are ignored
{"LF": [...], ...} Read in LF, RF, LR, RR order; the fourth item per leg is wheel
Explicit *_supplement Overrides wheel values produced by automatic splitting; fewer than 4 items are zero-filled

To avoid “correct length but wrong semantics”, custom algorithms should either always use the interleaved 16D form or always pass explicit 12+4 data groups. Do not mix the two.

Type Generation and Compatibility¶

After modifying root .lcm files, run:

bash scripts/generate_lcm_types.sh

The LCM type hash depends on field names, types, lengths, and order. After protocol changes, synchronize:

  1. Generated types used by the controller.
  2. Generated types in yobotics_sdk.
  3. Types imported by Python external algorithms.
  4. Viewer and monitor tools.
  5. The other endpoint in cross-machine runs.

The same number of fields does not imply compatibility. If a channel is visible but decoding fails, first check for mixed old generated files.

Acceptance Checklist¶

  • [ ] The 16D algorithm order is checked item by item, not only by length.
  • [ ] The four wheels enter supplement indices 0 through 3 correctly.
  • [ ] robot_id is Y20W.
  • [ ] Position, velocity, torque, Kp, and Kd are split in the same order.
  • [ ] Temperature and faults are read from raw joint state, not mistaken for development-state fields.
  • [ ] All communication processes use the same LCM type version.

After protocol checks, continue to DEVELOPMENT Mode.
