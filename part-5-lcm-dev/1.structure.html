5.1 Communication Architecture and Channels¶

This chapter explains where Y20W external algorithms sit in the communication path and how to confirm that state and commands really reach the target process. External algorithms interact with the controller through LCM and do not access MuJoCo, SPI, or motor drivers directly.

Data Flow¶

Gamepad / SDK / WebRTC
        |
        v
QUAD_ROBOT_CONTROL_Y20W
        |
        v
  Y20W controller state machine <----> MuJoCo or hardware layer
        |
        +-- Y20W_development_state --> external algorithm
        |                                  |
        +< Y20W_development_command -------+
        |
        +-- QUAD_ROBOT_STATE_Y20W ------> SDK / WebRTC / Viewer

The controller handles mode switching, safety checks, and final joint-command output. External algorithms only read state and submit targets through the DEVELOPMENT link. Even if an algorithm is publishing commands, those targets are not valid control input until the controller enters DEVELOPMENT.

Channel Responsibilities¶

Channel Message type Main publisher Main subscriber Purpose Frequency source
Y20W_QUAD_JOINT_STATE quad_joint_state_t MuJoCo or hardware layer Controller, Viewer, SDK Raw 12+4 joint, driver, temperature, and fault state Hardware layer or simulation loop
Y20W_QUAD_JOINT_COMMAND quad_joint_command_t Controller MuJoCo or hardware layer Low-level targets from controller to 12+4 actuators Controller cycle
Y20W_QUAD_IMU_DATA microstrain_lcmt MuJoCo or IMU layer Controller Quaternion, posture, angular velocity, and acceleration IMU or simulation cycle
QUAD_ROBOT_CONTROL_Y20W sport_client_cmd_t SDK, WebRTC Controller High-level mode, velocity, and body-posture commands Client send cycle
QUAD_ROBOT_STATE_Y20W sport_client_state_t Controller SDK, WebRTC, Viewer Application-level battery, posture, state, and fault summary Controller publish cycle
Y20W_development_state development_state_t Controller External algorithm 12+4 state, IMU, and desired velocity for development mode Controller publish cycle
Y20W_development_command development_command_t External algorithm Controller 12+4 position, velocity, torque, and PD targets execution.lcm_send_frequency

The package does not define one fixed frequency for all state channels. Acceptance should be based on continuity and measured frequency. The two example algorithms use their own configured command frequencies: walk defaults to 500 Hz, and wave defaults to 200 Hz.

Do not mix the three command channel types

Y20W_QUAD_JOINT_COMMAND is the controller output to the lower layer, QUAD_ROBOT_CONTROL_Y20W is the high-level input to the state machine, and Y20W_development_command is the external-algorithm entry. Custom algorithms should not impersonate the controller by publishing the low-level joint channel directly.

Source of the LCM URL¶

External algorithms read lcm.url from config.yaml:

  • When non-empty, that URL is used directly.
  • When it is an empty string, a default LCM instance is created and network configuration comes from the system environment.
  • The common project multicast address is udpm://239.255.76.67:7667?ttl=255.

Set it explicitly before startup if needed:

export LCM_DEFAULT_URL='udpm://239.255.76.67:7667?ttl=255'

ttl determines how many network hops multicast data may pass through. It does not replace correct routing, interface selection, or firewall setup. Both sides must use the same multicast address and port.

Three Runtime Topologies¶

Single Machine, Single Terminal¶

Suitable for quick validation. Start simulation first, then start the algorithm in another terminal:

bash scripts/start_mujoco.sh

python3 external_algorithms/wave_algorithm/run_algorithm.py   --config external_algorithms/wave_algorithm/config.yaml

Single Machine, Multiple Terminals¶

Recommended for development. Run the controller, monitor, and algorithm separately to separate log sources:

# Terminal 1
bash scripts/start_mujoco.sh

# Terminal 2
bash scripts/monitor_lcm.sh --no-gui

# Terminal 3
python3 external_algorithms/wave_algorithm/run_algorithm.py   --config external_algorithms/wave_algorithm/config.yaml

Cross-Machine¶

The controller and algorithm host should be on a network that permits UDP multicast. Run network configuration on both sides and confirm matching environment variables:

sudo bash scripts/setup_lcm_network.sh
source ~/.lcm_network_config
printf '%s
' "$LCM_DEFAULT_URL"

Then verify the state channel before running any algorithm that publishes commands. Do not treat “ping works” as “LCM multicast works”; they use different protocols and routing behavior.

Communication Acceptance¶

Use the Project Monitor Script¶

bash scripts/monitor_lcm.sh --no-gui

With a desktop environment, start the graphical monitor:

bash scripts/monitor_lcm.sh

Acceptance order:

  1. After starting the controller, confirm Y20W_development_state appears continuously.
  2. After starting the algorithm, confirm Y20W_development_command appears.
  3. Check that robot_id is Y20W in both messages.
  4. Check that command frequency is close to the algorithm configuration and has no long dropouts.
  5. After switching to DEVELOPMENT, observe whether joint state responds continuously.

Use lcm-spy¶

If the LCM Java tools are installed, run:

lcm-spy

lcm-spy can show channel names and frequencies. Fields can only be expanded correctly after matching LCM types are loaded. If a channel appears but cannot be decoded, the type definition, generated code, or class path is usually inconsistent.

Troubleshooting¶

Symptom Check Common cause Handling
No Y20W channels are visible LCM_DEFAULT_URL, interface, controller process Controller not started or URL mismatch Unify URL, rerun network setup, and verify controller first
Channels appear locally but not on another machine Multicast route, firewall, switch Network blocks UDP multicast Test on the same subnet, open the port, and check multicast config
Channel visible but fields cannot expand LCM types and type hash Old generated types are being used Regenerate from current .lcm and sync all components
State exists but no command Algorithm startup log and config path Algorithm not running, did not receive state, or init failed Check dependencies, model path, and robot_id
Command exists but robot does not respond mode, enable fields, state-machine logs Controller has not entered DEVELOPMENT Check each stage in DEVELOPMENT Lifecycle
Command frequency is much lower than expected CPU usage, inference time, network Inference blocks or send thread scheduling is insufficient Reduce debug printing, measure inference time, and validate in simulation first

Success Indicators¶

  • State and command use the same LCM URL.
  • Y20W_development_state updates continuously and robot_id is correct.
  • After algorithm startup, the command channel reaches the configured frequency range without persistent loss.
  • After DEVELOPMENT activation, joint response direction matches algorithm targets.
  • When the algorithm stops, a disable command is visible and the robot switches back to a safe mode.
