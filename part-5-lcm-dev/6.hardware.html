5.6 Custom Algorithms and Hardware Integration¶

This chapter moves a custom algorithm from directory creation through simulation validation to low-speed hardware testing. Each stage has pass conditions. If any critical item fails, stay in the current stage and fix it instead of reducing attention and continuing to hardware.

Create a New Algorithm from wave¶

Keep the wave example unchanged and copy its directory as your starting point:

cp -r external_algorithms/wave_algorithm   external_algorithms/my_algorithm

Then modify:

  1. algorithm_name in config.yaml.
  2. Class description and startup prompts in run_algorithm.py.
  3. _run_inference() or model-loading logic.
  4. Observation definition in compute_observation().
  5. Action semantics and safety checks in process_action().
  6. The standalone README with dependencies, startup commands, and parameters.

The new directory should contain at least:

my_algorithm/
├── config.yaml
├── run_algorithm.py
└── README.md

Do not modify global algorithm_base.py just to accommodate one model. Put model-specific behavior in the subclass first. Only move capabilities into the base class when multiple algorithms need them and the interface is stable.

Three Implementation Styles¶

Type Configuration/implementation Suitable for
Rule algorithm policy.type: none, override _load_policy() and _run_inference() Sine waves, trajectories, classical controllers, communication validation
Single ONNX model Override _load_policy() and _run_inference() yourself Models with one session and inputs/outputs different from the example
Encoder + Actor Reuse base ONNX inference and override observation/action handling as needed Recurrent model structure matching walk

The base class currently requires both encoder and actor for its native ONNX path. An actor-only model cannot run just by leaving encoder_path empty; implement single-model loading and inference explicitly in the subclass.

Configuration Design¶

Keep these groups:

algorithm_name: "my_algorithm"

policy:
  type: "none"
  model_path: ""
  encoder_path: ""
  read_metadata: false
  warmup_count: 0
  action_threshold: 20.0

model_params:
  num_actions: 16
  num_obs: 57
  default_joint_pos: []
  joint_stiffness: []
  joint_damping: []
  action_scale: []

lcm:
  url: ""
  state_channel: "Y20W_development_state"
  command_channel: "Y20W_development_command"
  robot_id: "Y20W"

execution:
  frequency: 50.0
  lcm_send_frequency: 500.0
  auto_start: true
  auto_end: true
  max_execution_time: 0.0

Do not use “reasonable-looking” placeholder arrays on hardware. default_joint_pos, Kp, Kd, and action_scale must come from validated model deployment parameters.

Observation Principles¶

  • Document each segment's index, unit, coordinate frame, and scale in docs or comments.
  • Validate raw state before reordering and normalization.
  • Define quaternion order explicitly; stationary and translation tests do not replace single-axis tilt tests.
  • Reset historical observations and recurrent state every time DEVELOPMENT is entered.
  • Check state freshness using timestamps or receive time.
  • Reject NaN/Inf and record the specific segment instead of printing only the full vector.
  • Use clipping only as final protection, not to hide unit or scaling errors.

Action Principles¶

  • Validate output type, shape, and finite values first.
  • Define whether model output is absolute position, position offset, velocity, or torque.
  • Apply action scaling per axis; do not assume legs and wheels use the same scale.
  • Limit target position, velocity, torque, and gains separately.
  • Check cycle-to-cycle rate of change to avoid single-frame jumps.
  • Define whether no-new-action behavior is hold, decay, or exit.
  • Use fixed functions for 16D interleaved layout and 12+4 protocol conversion.
  • Write only complete command frames into the cache so the send thread cannot read half-updated data.

joint_mapping¶

Example configs include:

joint_mapping:
  model_joint_order: []
  robot_joint_order: []
  enabled: false

The current wave and walk runtime paths do not automatically apply a generic joint mapping. Both handle observation and action in fixed Y20W order. Changing only enabled to true will not perform reordering automatically.

If the model joint order is different, implement explicit index mapping in the custom algorithm and verify that forward and reverse mappings are inverse processes:

robot state order -> model input order -> model output order -> robot command order

Six-Stage Acceptance¶

Stage 1: Offline Model Check¶

Do not start the controller. Check only files and inference interfaces.

Pass conditions:

  • Model loads successfully.
  • Input count, names, shape, and dtype are clear.
  • A fixed test vector repeatedly produces finite output.
  • All parameter arrays have correct lengths.
  • Observation and action indices are defined in writing.

Do not continue if output contains NaN/Inf, shape depends on guessing, joint order is unclear, or parameters are placeholders.

Stage 2: LCM Read-Only State¶

Start the controller and monitor, but do not publish valid joint targets. Check:

  • robot_id=Y20W.
  • 12+4 positions, velocities, and torques are readable.
  • Quaternion, RPY, angular velocity, and acceleration are reasonable.
  • Desired velocity fields change with control input.
  • State is continuous with no obvious long dropouts.

Do not continue if state dimensions are wrong, quaternion order is uncertain, wheel supplement is persistently abnormal, or channels often drop out.

Stage 3: MuJoCo Low-Gain Validation¶

Use conservative actions and gains in MuJoCo:

  1. Enter and exit with zero action.
  2. Test only one joint or one command axis at a time.
  3. Verify four-leg and wheel order.
  4. Verify DEVELOPMENT switching.
  5. Simulate Ctrl+C and algorithm abnormal exit.

Pass when action direction, zero position, frequency, and exit path are all correct, with no persistent oscillation or target jump.

Stage 4: Continuous Run and Failure Validation¶

Run longer in simulation and actively test:

  • Pause state publishing.
  • Stop command publishing.
  • Create one invalid observation or action.
  • Make inference time exceed the target period.
  • Interrupt the network or switch to a wrong LCM URL.
  • End the algorithm during motion.

Pass when logs, controller behavior, and manual recovery steps are confirmed for each exception and no unexplained persistent command remains.

Stage 5: Stand-Supported Hardware, Low Amplitude¶

Prerequisites:

  • The robot is reliably fixed; wheels and feet cannot contact personnel.
  • Emergency stop is available and assigned to a dedicated person.
  • Power, SPI, IMU, clock, and joint state are normal.
  • Temperature, faults, and driver state are visible.
  • A separate conservative configuration is used, with amplitude, speed, and gains lower than simulation validation values.

Verify zero action first, then single-leg, single-axis, and low-frequency motion. Stop immediately for any wrong direction, abnormal noise, temperature rise, fault code, or communication interruption.

Stage 6: Low-Speed Ground Test¶

Run only after stand-supported tests pass. Choose an open, flat area, limit speed and runtime, and verify one velocity axis at a time. Keep emergency stop, towing, or power-off options onsite and continuously observe posture and wheel speed.

Pass when startup, velocity following, zero-command recovery, mode exit, and emergency stop are repeatable with no faults, abnormal temperature rise, or control-frequency drop.

Hardware Startup Order¶

1. Before Power-On¶

  • Check mechanical connections and wheel/joint motion ranges.
  • Confirm robot fixation and emergency stop.
  • Confirm configuration uses the correct SPI board type, IMU, power, and clock devices.
  • Confirm no personnel are inside joint or wheel motion ranges.

2. Start Controller¶

sudo bash scripts/run_robot_controller.sh --config config.yaml

The script selects bin/lib or bin_rk3588/lib_rk3588 according to system architecture. This manual does not include RK3588 build or deployment flow.

3. Read-Only Check¶

bash scripts/monitor_lcm.sh --no-gui

Start the hardware Viewer if needed:

bash scripts/start_hardware_viewer.sh

4. Start Algorithm¶

Validate with wave first, then start your custom algorithm:

python3 external_algorithms/my_algorithm/run_algorithm.py   --config external_algorithms/my_algorithm/config.yaml

5. Switch Mode¶

Enter DEVELOPMENT only after algorithm warmup and checks complete. Immediately verify mode, posture, and joint response after switching.

Runtime Monitoring¶

Metric Source Watch for
RPY, quaternion development state or IMU Jumps, drift, wrong direction
Joint position 12+4 state Target tracking, limits, jumps
Joint velocity and wheel speed 12+4 state Abnormal high speed, direction, persistent rotation
Joint torque 12+4 state Sudden rise, long high load
Temperature Raw joint state Continuous rise or single-motor abnormality
Fault and driver state Raw joint state Any non-normal state
State frequency LCM monitor Dropouts and jitter
Command frequency LCM monitor Below config or unstable period
Inference time Algorithm log/custom stats Exceeds inference period
Observation/action range Algorithm stats Clipping, saturation, NaN/Inf

Normal Exit¶

  1. Reduce velocity command to zero.
  2. Switch back to DAMP or the current safe mode.
  3. Confirm joints and wheels have stopped.
  4. Press Ctrl+C to end the algorithm.
  5. Confirm enable_development_mode=0 was sent.
  6. Stop the controller and power off according to onsite procedure.

Do not make closing the algorithm terminal the first step. The send thread tries to send about 100 ms of end commands during normal exit, but forced process kill, power loss, or interpreter crash may bypass that flow.

Failure Handling¶

Failure Immediate action Check before recovery
State timeout or LCM interruption Switch to safe mode or emergency stop; do not keep old action URL, interface, controller, and state freshness
Algorithm crash Use an independent control entry to exit DEVELOPMENT Last command frame, exit log, and controller mode
Consecutive inference failures Stop policy and withdraw motion command Input, model, CPU load, recurrent state
Action NaN/Inf or out of range Stop publishing immediately and exit mode Trigger observation, scaling, model output, and limits
Wrong joint direction Emergency stop; do not blindly flip a global sign Single-joint index, axis direction, and model order
Temperature or fault abnormality Stop motion and power off/check by hardware procedure Corresponding motor, driver, cable, and load
High-frequency vibration Immediately switch to DAMP or emergency stop PD, control period, delay, zero position, and mechanical state

The current example framework does not fully implement automatic state-timeout shutdown, joint limits, or consecutive-failure thresholds. Before hardware deployment, custom algorithms should add these policies or confirm the controller side already provides them and test the real trigger behavior.

Final Acceptance Checklist¶

  • [ ] The algorithm and robot joint order have an item-by-item mapping table.
  • [ ] Every observation segment's unit, coordinate frame, scaling, and clipping are recorded.
  • [ ] Action semantics, scaling, default posture, and PD parameters come from the same training/deployment configuration.
  • [ ] wave, zero action, single joint, and single velocity axis validations all pass.
  • [ ] State interruption, model exception, and algorithm exit results have been tested.
  • [ ] Raw joint temperature, faults, and driver state are included in monitoring.
  • [ ] Hardware uses a separate conservative configuration with stand and emergency stop.
  • [ ] After normal exit, the controller is no longer in DEVELOPMENT.
