5.5 ONNX Walking Example¶

walk_algorithm uses two ONNX models, an encoder and an actor, to convert Y20W state into a 57D observation and output a 16D wheel-leg action. This example demonstrates the complete policy-inference path and requires the training conventions and deployment side to match exactly.

Execution Chain¶

development_state_t
  -> state reorder and scaling
  -> 57D observation
  -> HumanEncodernet.onnx + recurrent state
  -> latent
  -> HumanActornet.onnx + recurrent state
  -> 16D action
  -> scaling + default posture
  -> q/qd/tau/Kp/Kd
  -> development_command_t (12+4)

The encoder must have 3 inputs: observation, hidden, and cell. The actor must have 4 inputs: observation, latent, hidden, and cell. The code reads actual input names and last-dimension shapes from ONNX sessions and maintains two recurrent-state groups.

Startup Command¶

python3 external_algorithms/walk_algorithm/run_algorithm.py   --config external_algorithms/walk_algorithm/config.yaml

Relative model paths are resolved from the configuration file directory, so the defaults load:

external_algorithms/walk_algorithm/HumanEncodernet.onnx
external_algorithms/walk_algorithm/HumanActornet.onnx

Use wave to validate communication and joint mapping before startup. That keeps ONNX issues separate from lower-level link issues.

Configuration and Precedence¶

Policy¶

Field Default Description
policy.type onnx Use ONNX Runtime
model_path ./HumanActornet.onnx actor model
encoder_path ./HumanEncodernet.onnx encoder model
read_metadata false Uses model parameters from YAML directly
warmup_count 500 Runs 500 warmup inferences with real state
action_threshold 100.0 Absolute action threshold during warmup

Model Parameters¶

Field Default summary Purpose
num_obs 57 Observation length
num_actions 16 Action length
default_joint_pos Per leg [0, -0.8, 1.6, 0] Position target reference
joint_stiffness Legs 8, wheels 0 Kp
joint_damping Legs 0.2, wheels 0.5 Kd
action_scale Legs 0.25, wheels 10 Per-axis scale from action to target
dof_pos_scale 1.0 Joint position error scale
dof_vel_scale 0.05 Joint velocity scale
ang_vel_scale 0.25 Body angular velocity scale
command_scale 2.0 Velocity command scale
lin_vel_scale 2.0 Present in config, but current 57D observation has no body linear-velocity item

When read_metadata: false, YAML is the deployment-parameter source. If set to true and the onnx package is installed, the code reads joint_names, default positions, Kp, Kd, action scale, action dimension, and observation dimension from actor metadata and overrides the corresponding in-memory parameters.

Warning

If metadata reading fails, the current code only prints a warning and may continue with YAML parameters. After enabling this function, read the startup log; do not infer final parameters from the config file alone.

57D Observation¶

Index Length Data Processing
0:3 3 state.omega[0:3] Multiply by ang_vel_scale
3:6 3 Gravity projection computed from quaternion No extra scaling
6:9 3 [v_des[0], v_des[1], omega_des[2]] Multiply by command_scale
9:25 16 (dof_q - default_joint_pos) Multiply by dof_pos_scale
25:41 16 dof_qd Multiply by dof_vel_scale
41:57 16 Previous action_buffer Written as-is

Total dimension is 3 + 3 + 3 + 16 + 16 + 16 = 57.

Angular Velocity¶

Angular velocity is taken directly from development_state_t.omega. Training and deployment must use the same body frame, axis direction, and units.

Gravity Projection¶

The code computes gravity direction in the body frame using quaternion [w, x, y, z]. This provides roll/pitch posture information to the policy while avoiding Euler-angle discontinuities.

If the upstream quaternion order is [x, y, z, w], the computation still runs but the observation semantics are completely wrong. When replacing the state source, first test stationary posture and single-axis tilts.

Velocity Command¶

The observation uses:

[forward velocity v_des[0], lateral velocity v_des[1], yaw rate omega_des[2]]

v_des[2] and omega_des[0:2] do not enter the current policy observation.

Joint Position and Velocity¶

LCM 12+4 state is reordered to:

[LF_hip, LF_thigh, LF_calf, LF_wheel,
 RF_hip, RF_thigh, RF_calf, RF_wheel,
 LR_hip, LR_thigh, LR_calf, LR_wheel,
 RR_hip, RR_thigh, RR_calf, RR_wheel]

Position subtracts default_joint_pos; velocity does not subtract zero position. Both are multiplied by their own scales.

Historical Action¶

action_buffer starts as all zeros. After each successful inference and finite-value check, the base class saves the current action under lock; the next observation reads it as the final 16D input.

Observation Clipping¶

compute_observation() uses model_params.obs_clip_range; if missing, it clips to [-100, 100] by default. The base class also clips observations whose absolute values exceed 100 before inference.

Clipping can prevent numeric explosion, but persistent clipping usually means scaling, units, or sensor state are wrong. Fix the source instead of relying on clipping.

Encoder and Actor Inference¶

Encoder¶

  1. Read the three input names and last dimensions.
  2. Reshape observation to (1, obs_dim).
  3. On first run, initialize hidden and cell as zero arrays with shape (1, 1, hidden_dim).
  4. Run encoder.
  5. Save output latent, new hidden, and new cell.

Actor¶

  1. Read four inputs: observation, latent, hidden, cell.
  2. Reshape observation and latent as 2D batches.
  3. Initialize or reuse actor recurrent state.
  4. Run actor.
  5. Flatten the first output and convert it to float32 action.
  6. If hidden/cell outputs exist, update recurrent state.

Every time DEVELOPMENT starts again, encoder and actor recurrent states are cleared.

16D Action Processing¶

process_action() performs:

  1. Reject None or empty actions.
  2. Check NaN/Inf.
  3. On abnormal action, try to read the current action_buffer.
  4. Check that action_scale matches action length.
  5. Check and pad default_joint_pos.
  6. Compute position and velocity targets.
  7. Check that results are finite and exactly length 16.
  8. Read Kp and Kd.
  9. Update the latest command cache for the send thread.

Current computation:

q_des  = action * action_scale + default_joint_pos
qd_des = action * action_scale
tau_des = 0

Wheel action_scale defaults to 10; leg joints default to 0.25. This reflects the current model deployment convention and must not be copied directly to models with different output semantics.

Boundary of NaN fallback

The base class rejects NaN/Inf before updating action_buffer, so the walk fallback usually uses the most recent valid action. Holding an old action continuously is not necessarily safe; custom algorithms should add action freshness and consecutive-failure handling.

Model Warmup¶

Default warmup runs 500 inferences with real state:

  1. Wait for Y20W_development_state.
  2. Build the 57D observation.
  3. Run encoder and actor.
  4. Check whether each action absolute value exceeds 100.
  5. Print progress and successful inference count.
  6. If abnormal actions remain at the end, print observation, action, and abnormal indices, then exit.

Warmup requires the controller to publish state continuously, but it does not mean joint commands are active. Passing warmup only means the model can run on the current state and did not trigger that action threshold.

Simulation Acceptance Flow¶

  1. Use wave to validate the DEVELOPMENT link and 16D order.
  2. Start walk without entering DEVELOPMENT, and observe model loading plus 500 warmup runs.
  3. Confirm a reasonable warmup success count and no action-threshold, NaN, or shape errors.
  4. Keep velocity command at zero, enter DEVELOPMENT, and check standing and switching continuity.
  5. Send small forward, lateral, and yaw commands one axis at a time.
  6. Check that motion returns to stable state after commands are zeroed.
  7. Run longer and watch inference errors, frequency drop, state dropouts, and posture drift.
  8. Validate exit behavior for Ctrl+C, mode switching, and controller stop.

Recommended records: state and command frequencies, inference time, maximum absolute observation, maximum absolute action, posture, 16D position/velocity, wheel speed, and exception count.

Troubleshooting¶

Symptom Check Cause Handling
Model not found Config path and current directory Relative path resolved from the wrong location Use the project-root command or check model location relative to config
onnxruntime cannot import Python environment Dependency not installed in current interpreter Activate project environment and run python3 -c 'import onnxruntime'
Encoder input count wrong ONNX input list Model structure does not match current 3-input convention Modify deployment adapter or export a matching model
Actor input count wrong ONNX input list Model structure does not match current 4-input convention Do not only change config dimensions; adapt inference code
metadata does not take effect read_metadata, onnx package, startup log Metadata missing or parse failed Check logs and return to explicit YAML parameters
Warmup success count is 0 State channel and robot_id No real state received Fix communication before entering DEVELOPMENT
Observation often clipped Raw state, units, scaling Sensor abnormality or training normalization mismatch Print observation segments and locate source
Output has NaN/Inf Input, recurrent state, model Model numeric instability Exit mode, save trigger frame, and reproduce offline
Robot vibrates after entering mode Default posture, PD, control period Zero position or gain mismatch Switch to DAMP and lower gains in simulation
Velocity does not follow v_des, omega_des, command_scale Upstream command missing from observation or scaling mismatch Monitor state fields and observation indices 6:9
Wheel and leg actions are mismatched 16D reorder and supplement Used incorrect first-12-plus-last-4 order Check item by item against the index table

Success Indicators¶

  • Both models load and input counts/shapes match code expectations.
  • 500 warmup runs complete without final action overflow.
  • Each 57D observation segment matches training conventions.
  • 16D action reorder, default posture, and scaling are all checked.
  • Zero command and small single-axis commands run repeatably in simulation.
  • After abnormal exit, the controller returns to a safe mode.

After these pass, follow Custom Algorithms and Hardware Integration for staged validation.
