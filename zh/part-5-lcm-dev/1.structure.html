5.1 通信结构与通道¶

本章说明 Y20W 外部算法所处的通信位置，以及如何确认状态和命令真正到达目标进程。外部算法通过 LCM 与控制器交互，不直接访问 MuJoCo、SPI 或电机驱动。

数据流¶

手柄 / SDK / WebRTC
        |
        v
QUAD_ROBOT_CONTROL_Y20W
        |
        v
  Y20W 控制器状态机 <----> MuJoCo 或实机硬件层
        |
        +-- Y20W_development_state --> 外部算法
        |                                  |
        +< Y20W_development_command -------+
        |
        +-- QUAD_ROBOT_STATE_Y20W ------> SDK / WebRTC / Viewer

控制器负责模式切换、安全检查和最终关节命令输出。外部算法只在 DEVELOPMENT 链路上读取状态并提交目标值。即使算法已经发布命令，控制器没有进入 DEVELOPMENT 时也不会把这些目标作为有效控制输入。

通道职责¶

通道 消息类型 主要发布方 主要订阅方 用途 频率来源
Y20W_QUAD_JOINT_STATE quad_joint_state_t MuJoCo 或硬件层 控制器、Viewer、SDK 原始 12+4 关节、驱动、温度和故障状态 硬件层或仿真循环
Y20W_QUAD_JOINT_COMMAND quad_joint_command_t 控制器 MuJoCo 或硬件层 控制器输出到 12+4 执行器的底层目标 控制器周期
Y20W_QUAD_IMU_DATA microstrain_lcmt MuJoCo 或 IMU 层 控制器 四元数、姿态、角速度和加速度 IMU 或仿真周期
QUAD_ROBOT_CONTROL_Y20W sport_client_cmd_t SDK、WebRTC 控制器 高层模式、速度和机身姿态指令 客户端发送周期
QUAD_ROBOT_STATE_Y20W sport_client_state_t 控制器 SDK、WebRTC、Viewer 面向应用的电量、姿态、状态和故障摘要 控制器发布周期
Y20W_development_state development_state_t 控制器 外部算法 开发模式所需的 12+4 状态、IMU 和期望速度 控制器发布周期
Y20W_development_command development_command_t 外部算法 控制器 12+4 位置、速度、扭矩和 PD 目标 execution.lcm_send_frequency

开发包没有为所有状态通道规定统一的固定频率。验收时应以连续性和实际测得频率为准。两个示例算法的命令频率分别来自各自配置：walk 默认 500 Hz，wave 默认 200 Hz。

不要混用三类命令通道

Y20W_QUAD_JOINT_COMMAND 是控制器到底层的输出，QUAD_ROBOT_CONTROL_Y20W 是应用到状态机的高层输入，Y20W_development_command 才是外部算法入口。自研算法不要直接冒充控制器发布底层关节通道。

LCM URL 的来源¶

外部算法读取 config.yaml 中的 lcm.url：

  • 非空时直接使用该 URL；
  • 空字符串时创建默认 LCM 实例，由系统环境决定网络配置；
  • 项目常用多播地址为 udpm://239.255.76.67:7667?ttl=255。

可在启动前显式设置：

export LCM_DEFAULT_URL='udpm://239.255.76.67:7667?ttl=255'

ttl 决定多播数据允许经过的网络跳数。它不能代替正确的路由、网卡选择或防火墙设置。通信双方必须使用相同的多播地址和端口。

三种运行拓扑¶

单机单终端¶

适合快速验证。先启动仿真，再在另一个终端启动算法：

bash scripts/start_mujoco.sh

python3 external_algorithms/wave_algorithm/run_algorithm.py \
  --config external_algorithms/wave_algorithm/config.yaml

单机多终端¶

推荐开发方式。分别运行控制器、监控器和算法，便于区分日志来源：

# 终端 1
bash scripts/start_mujoco.sh

# 终端 2
bash scripts/monitor_lcm.sh --no-gui

# 终端 3
python3 external_algorithms/wave_algorithm/run_algorithm.py \
  --config external_algorithms/wave_algorithm/config.yaml

跨机器¶

控制器与算法主机应处于允许 UDP 多播的网络中。两端分别执行网络配置并确认环境变量一致：

sudo bash scripts/setup_lcm_network.sh
source ~/.lcm_network_config
printf '%s\n' "$LCM_DEFAULT_URL"

随后先验证状态通道，再运行会发布命令的算法。不要把“能 ping 通”当作“LCM 多播可用”，二者使用的协议和路由行为不同。

通信验收¶

使用项目监控脚本¶

bash scripts/monitor_lcm.sh --no-gui

有桌面环境时可启动图形监控：

bash scripts/monitor_lcm.sh

验收顺序：

  1. 启动控制器后确认 Y20W_development_state 持续出现。
  2. 启动算法后确认 Y20W_development_command 出现。
  3. 检查两条消息中的 robot_id 都为 Y20W。
  4. 检查命令频率与算法配置接近，且没有长时间断流。
  5. 切换到 DEVELOPMENT 后观察关节状态是否连续响应。

使用 lcm-spy¶

系统安装了 LCM Java 工具时可以运行：

lcm-spy

lcm-spy 能看到通道名和频率；只有加载了匹配的 LCM 类型后才能正确展开字段。出现通道但无法解码，通常是类型定义、生成代码或类路径不一致。

故障定位¶

现象 检查 常见原因 处理
看不到任何 Y20W 通道 LCM_DEFAULT_URL、网卡、控制器进程 控制器未启动或 URL 不一致 统一 URL，重新执行网络配置并先验证控制器
本机有通道，另一台机器没有 多播路由、防火墙、交换机 网络阻止 UDP 多播 在同一网段测试，开放端口并检查多播配置
能看到通道但字段无法展开 LCM 类型和类型哈希 使用了旧生成类型 从当前 .lcm 重新生成并同步所有组件
有状态，没有命令 算法启动日志和配置路径 算法未运行、未收到状态或初始化失败 检查依赖、模型路径和 robot_id
有命令但机器人不响应 mode、使能字段、状态机日志 控制器未进入 DEVELOPMENT 按 DEVELOPMENT 生命周期核对每个阶段
命令频率明显偏低 CPU 占用、推理耗时、网络 推理阻塞或发送线程调度不足 降低调试打印，测量推理时间，先在仿真验证

成功标志¶

  • 状态和命令使用同一个 LCM URL。
  • Y20W_development_state 持续更新且 robot_id 正确。
  • 算法启动后命令通道达到配置量级，没有持续丢失。
  • DEVELOPMENT 激活后，关节响应与算法目标方向一致。
  • 停止算法时能够观察到禁用命令，并将机器人切回安全模式。
