6.4 Troubleshooting¶

The WebRTC path includes camera, encoding, signaling, ICE, DataChannel, and LCM. Validate by layer and avoid changing video parameters, network, and control protocol at the same time.

1. Process and Port¶

ss -lntp | grep 8765
Symptom Check Handling
Port not listening signaling_server.py logs and Python dependencies Fix dependency or port conflict, then restart the entry
Signaling started but publisher does not appear Whether an external client has connected The current manager waits for an external ready marker
Child processes restart repeatedly restart.flag and PeerConnection logs Locate signaling disconnect, ICE failure, or video-source failure first
Child process remains after Ctrl+C Manager cleanup log Wait for normal cleanup and confirm another service is not running

2. Video Source¶

USB mode:

ls -l /dev/video*

Check device index, permissions, occupying processes, and camera-supported resolution/frame rate.

RTSP mode should be verified first in a standalone player or OpenCV. The current default URL is local rtsp://127.0.0.1:8554/back, which requires a local RTSP service to already exist.

To exclude the real camera, set use_camera to false. If virtual video works but real video fails, the problem is in the video source or capture. If both fail, continue checking WebRTC negotiation.

3. Signaling and Connection¶

  • Remote clients must use the robot-reachable IP, not localhost.
  • Firewall must allow TCP 8765.
  • Logs should show client access, publisher registration, Offer, and Answer in order.
  • If duplicate or stale Answers are received, check whether the client created multiple sessions.
  • PeerConnection close requests restart; persistent close usually indicates ICE or network-path issues.

4. Video Quality and Latency¶

Tune in this order:

  1. Lower resolution first.
  2. Then lower max_fps.
  3. Adjust the three bitrate levels according to actual uplink bandwidth.
  4. Measure capture, encoding, network, and client rendering separately.
  5. Keep the control LCM link separately measurable.

5. DataChannel and Control¶

Symptom Check Handling
DataChannel opens but robot has no response QUAD_ROBOT_CONTROL_Y20W, rc_enable, current mode Confirm commands reach LCM and the controller accepts this mode
JSON parse error Client output string Send valid JSON only; do not send debug text on the same channel
LCM encode failure v, rpy, h, variable length Send complete arrays with numeric values
Mode changes but motion is unsafe Client limits and state-machine order Add range/rate limits and require state confirmation
State not returned QUAD_ROBOT_STATE_Y20W and LCM URL Verify controller state with SDK or monitor first

6. Safe Recovery¶

  • Client sends zero velocity and DAMP.
  • Confirm controller state through DataChannel or LCM monitor.
  • If the link is unavailable, use onsite control or emergency stop.
  • Stop control_publisher.py with Ctrl+C and wait for cleanup.
  • Do not restart repeatedly while the robot is still in an uncertain motion state.
