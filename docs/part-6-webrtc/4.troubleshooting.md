# 6.4 故障排查

WebRTC 链路包含摄像头、编码、信令、ICE、DataChannel 和 LCM。排查时按层验证，避免同时改视频参数、网络和控制协议。

## 1. 进程与端口

```bash
ss -lntp | grep 8765
```

| 现象 | 检查 | 处理 |
| --- | --- | --- |
| 端口未监听 | `signaling_server.py` 日志、Python 依赖 | 修复依赖或端口冲突后重启入口 |
| 信令已启动但 publisher 不出现 | 是否有外部客户端连接 | 当前管理器会等待外部就绪标记 |
| 子进程反复重启 | `restart.flag` 和 PeerConnection 日志 | 先定位信令断开、ICE 或视频源失败 |
| `Ctrl+C` 后仍有子进程 | 管理进程清理日志 | 等待正常清理，确认没有另一套服务 |

## 2. 视频源

USB 模式：

```bash
ls -l /dev/video*
```

检查设备索引、权限、占用进程和摄像头支持的分辨率/帧率。

RTSP 模式应先在独立播放器或 OpenCV 中确认 `rtsp_url` 可读。当前默认 URL 是本机 `rtsp://127.0.0.1:8554/back`，这要求本机已有 RTSP 服务。

排除真实摄像头时，将 `use_camera` 设为 `false`。虚拟画面可用而真实画面失败，问题位于视频源或采集；两者都失败则继续检查 WebRTC 协商。

## 3. 信令与连接

- 远端客户端使用机器人可达 IP，不使用 `localhost`；
- 防火墙允许 TCP 8765；
- 日志中应按顺序看到客户端接入、publisher 注册、Offer 和 Answer；
- 收到重复或过期 Answer 时检查客户端是否创建了多套会话；
- PeerConnection 关闭会请求重启，持续关闭通常是 ICE 或网络路径问题。

## 4. 视频质量与延迟

按以下顺序调整：

1. 先降低分辨率；
2. 再降低 `max_fps`；
3. 根据实际上行带宽调整三档码率；
4. 分别测量采集、编码、网络和客户端渲染；
5. 保持控制 LCM 链路单独可测。

低码率不一定降低延迟；过低会增加画面破碎或编码压力。日志中的上行速率只是诊断依据，应结合端到端画面观察。

## 5. DataChannel

| 现象 | 检查 | 处理 |
| --- | --- | --- |
| 有视频但无 DataChannel | 通道是否 open | 等待协商完成，不在 connecting 状态发送 |
| JSON 解析失败 | 消息是否是 JSON 字符串 | 固定客户端序列化和字段类型 |
| LCM 命令发送失败 | 数组长度、有限值、LCM 初始化 | 按 [DataChannel 协议](3.datachannel.md)校验 |
| 命令有通道但模式不变 | API 编号和状态机顺序 | 先发送 DAMP/站立并读取状态确认 |
| 断开后仍保持运动 | 客户端断连处理 | 立即使用独立控制入口清零并切回安全模式 |

## 6. LCM

```bash
bash scripts/monitor_lcm.sh --no-gui
```

确认：

- publisher 使用 `QUAD_ROBOT_CONTROL_Y20W`；
- 控制器发布 `QUAD_ROBOT_STATE_Y20W`；
- `config.json` 的 URL 与控制器一致；
- 多网卡环境的多播路由正确；
- 状态正常但控制异常时，API 编号和 `rc_enable` 符合预期。

## 安全恢复

如果远程控制失去响应：

1. 使用现场手柄、急停或独立安全入口停止机器人；
2. 确认控制器退出运动模式；
3. 再停止 WebRTC 服务；
4. 保存信令、publisher、控制器和 LCM 日志；
5. 在仿真或支架环境复现后再恢复远程控制。

不要在机器人仍运动时反复重启 WebRTC 进程来“抢回”控制权。
