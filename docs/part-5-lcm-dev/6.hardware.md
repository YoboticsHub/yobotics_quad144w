# 5.6 自定义算法与实机接入

本章把一个自定义算法从目录创建、仿真验证推进到实机低速测试。每个阶段都设置通过条件；任何关键项失败，都应停留在当前阶段修复，不应靠降低关注度继续上实机。

## 从 wave 创建新算法

推荐保留 wave 示例不变，复制其目录作为自己的算法起点：

```bash
cp -r external_algorithms/wave_algorithm \
  external_algorithms/my_algorithm
```

随后修改：

1. `config.yaml` 中的 `algorithm_name`；
2. `run_algorithm.py` 中的类说明和启动提示；
3. `_run_inference()` 或模型加载逻辑；
4. `compute_observation()` 的观测定义；
5. `process_action()` 的动作语义和安全检查；
6. 独立 README 中的依赖、启动命令和参数。

新目录至少应包含：

```text
my_algorithm/
├── config.yaml
├── run_algorithm.py
└── README.md
```

不要在新算法中修改全局 `algorithm_base.py` 来迁就单个模型。模型特有行为优先放在子类，只有多个算法共同需要且接口稳定的能力才适合下沉到基类。

## 三类实现方式

| 类型 | 配置/实现 | 适用情况 |
| --- | --- | --- |
| 规则算法 | `policy.type: none`，覆盖 `_load_policy()` 和 `_run_inference()` | 正弦、轨迹、传统控制器、通信验证 |
| 单 ONNX 模型 | 自行覆盖 `_load_policy()` 与 `_run_inference()` | 模型只有一个 session，输入输出不同于示例 |
| Encoder + Actor | 复用基类 ONNX 推理，按需覆盖观测和动作处理 | 与 walk 的循环模型结构一致 |

基类当前原生 ONNX 路径要求 encoder 和 actor 同时存在。只有 actor 的模型不能通过把 `encoder_path` 留空来直接运行，应在子类中明确实现单模型加载和推理。

## 配置设计

建议保留以下分组：

```yaml
algorithm_name: "my_algorithm"

policy:
  type: "none"
  model_path: ""
  encoder_path: ""
  read_metadata: false
  warmup_count: 0
  action_threshold: 20.0

model_params:
  num_actions: 16
  num_obs: 57
  default_joint_pos: []
  joint_stiffness: []
  joint_damping: []
  action_scale: []

lcm:
  url: ""
  state_channel: "Y20W_development_state"
  command_channel: "Y20W_development_command"
  robot_id: "Y20W"

execution:
  frequency: 50.0
  lcm_send_frequency: 500.0
  auto_start: true
  auto_end: true
  max_execution_time: 0.0
```

数组不要使用“看起来合理”的占位值上实机。`default_joint_pos`、Kp、Kd 和 `action_scale` 必须来自已验证的模型部署参数。

## 观测实现原则

- 在文档或代码注释中固定每一段索引、单位、坐标系和缩放；
- 先验证原始状态，再做重排和归一化；
- 对四元数明确顺序，静止和平移测试不能替代单轴倾斜测试；
- 历史观测和循环状态应在每次进入 DEVELOPMENT 时重置；
- 对状态时间戳或接收时间做新鲜度判断；
- 拒绝 NaN/Inf，并记录具体分段而不只打印整个向量；
- 裁剪应作为最后保护，不应掩盖单位或缩放错误。

## 动作处理原则

- 首先验证输出类型、shape 和有限值；
- 明确模型输出是绝对位置、位置偏移、速度还是扭矩；
- 逐轴应用动作缩放，不默认腿和 wheel 使用同一尺度；
- 对目标位置、速度、扭矩和增益分别限制；
- 检查相邻周期变化率，避免单帧跳变；
- 明确无新动作时是保持、衰减还是退出；
- 用固定函数完成 16 维交错布局与 12+4 协议转换；
- 命令缓存只写入完整的一帧，避免发送线程读到半更新数据。

## `joint_mapping`

示例配置包含：

```yaml
joint_mapping:
  model_joint_order: []
  robot_joint_order: []
  enabled: false
```

当前 wave 和 walk 的运行路径没有自动应用通用关节映射，二者在观测和动作代码中按 Y20W 固定顺序处理。仅把 `enabled` 改为 `true` 不会自动完成重排。

若模型关节顺序不同，应在自定义算法中实现明确的索引映射，并验证正向和反向映射互为逆过程：

```text
机器人状态顺序 -> 模型输入顺序 -> 模型输出顺序 -> 机器人命令顺序
```

## 六阶段验收

### 阶段 1：离线模型检查

不启动控制器，只检查文件和推理接口。

通过条件：

- 模型可以加载；
- 输入数量、名称、shape 和 dtype 明确；
- 使用固定测试向量能重复得到有限输出；
- 所有参数数组长度正确；
- 观测与动作索引已有书面定义。

禁止继续：输出包含 NaN/Inf、shape 依赖猜测、关节顺序不明确或参数由占位值组成。

### 阶段 2：LCM 只读状态

启动控制器和监控器，但不发布有效关节目标。检查：

- `robot_id=Y20W`；
- 12+4 位置、速度和扭矩均能读取；
- 四元数、RPY、角速度、加速度合理；
- 期望速度字段随控制输入变化；
- 状态连续且没有明显长时间断流。

禁止继续：状态维度错误、四元数顺序不确定、wheel supplement 恒为异常值或通道频繁中断。

### 阶段 3：MuJoCo 低增益验证

在 MuJoCo 中使用保守动作和增益：

1. 零动作进入和退出；
2. 每次只测试一个关节或一个命令轴；
3. 验证四条腿和 wheel 顺序；
4. 验证 DEVELOPMENT 切换；
5. 模拟 `Ctrl+C` 和算法异常退出。

通过条件：动作方向、零位、频率和退出路径全部正确，没有持续振荡或目标跳变。

### 阶段 4：连续运行与失效验证

在仿真中延长运行时间，并主动测试：

- 暂停状态发布；
- 停止命令发布；
- 制造一次非法观测或动作；
- 让推理耗时超过目标周期；
- 中断网络或切换错误 LCM URL；
- 在运动中结束算法。

通过条件：每种异常的日志、控制器行为和人工恢复步骤都已确认，不会产生无法解释的持续命令。

### 阶段 5：支架实机低幅值测试

前置条件：

- 机器人可靠固定，轮子和足端不会接触人员；
- 急停可用且有人专门负责；
- 电源、SPI、IMU、时钟和关节状态正常；
- 温度、故障与驱动状态可见；
- 使用单独的保守配置，幅值、速度和增益低于仿真验证值。

先验证零动作，再验证单腿、单轴和低频动作。任何方向错误、异常噪声、温升、故障码或通信中断都应立即停止。

### 阶段 6：地面低速测试

仅在支架测试通过后进行。选择空旷、平整区域，限制速度和运行时间，一次只验证一个速度轴。现场应保留急停、拖拽或断电条件，并持续观察姿态和轮速。

通过条件：起步、速度跟随、零命令恢复、模式退出和急停均可重复，且没有故障、异常温升或控制频率下降。

## 实机启动顺序

### 1. 上电前

- 检查机械连接、轮子和关节活动范围；
- 确认机器人固定方式和急停；
- 确认配置使用正确 SPI 板型、IMU、电源和时钟设备；
- 确认现场没有人员处于关节和轮子的运动范围内。

### 2. 启动控制器

```bash
sudo bash scripts/run_robot_controller.sh --config config.yaml
```

脚本会根据系统架构选择 `bin/lib` 或 `bin_rk3588/lib_rk3588`。本说明书不包含 RK3588 构建或部署流程。

### 3. 只读检查

```bash
bash scripts/monitor_lcm.sh --no-gui
```

必要时启动硬件 Viewer：

```bash
bash scripts/start_hardware_viewer.sh
```

### 4. 启动算法

先用 wave 验证，再启动自研算法：

```bash
python3 external_algorithms/my_algorithm/run_algorithm.py \
  --config external_algorithms/my_algorithm/config.yaml
```

### 5. 切换模式

确认算法预热和检查完成后，才进入 DEVELOPMENT。切换后立即核对 `mode`、姿态和关节响应。

## 运行监控

| 指标 | 来源 | 关注点 |
| --- | --- | --- |
| RPY、四元数 | development 状态或 IMU | 突变、漂移、方向错误 |
| 关节位置 | 12+4 状态 | 目标跟踪、限位和跳变 |
| 关节速度与轮速 | 12+4 状态 | 异常高速、方向和持续旋转 |
| 关节扭矩 | 12+4 状态 | 突增、长期高负载 |
| 温度 | 原始关节状态 | 持续升高或单电机异常 |
| 故障与驱动状态 | 原始关节状态 | 任一非正常状态 |
| 状态频率 | LCM 监控 | 断流和抖动 |
| 命令频率 | LCM 监控 | 低于配置或周期不稳定 |
| 推理耗时 | 算法日志/自定义统计 | 超过推理周期 |
| 观测/动作范围 | 算法统计 | 裁剪、饱和、NaN/Inf |

## 正常退出

1. 把速度命令降为零。
2. 切回 DAMP 或当前安全模式。
3. 确认关节和 wheel 已停止。
4. 按 `Ctrl+C` 结束算法。
5. 确认 `enable_development_mode=0` 已发送。
6. 停止控制器并按现场流程断电。

不要把关闭算法终端作为第一步。发送线程会在正常退出时尝试发送约 100 ms 的结束命令，但强制杀进程、断电或解释器崩溃可能绕过该流程。

## 失效处理

| 失效 | 立即动作 | 恢复前检查 |
| --- | --- | --- |
| 状态超时或 LCM 中断 | 切回安全模式或急停，不继续保持旧动作 | URL、网卡、控制器和状态新鲜度 |
| 算法崩溃 | 使用独立控制入口退出 DEVELOPMENT | 最后一帧命令、退出日志和控制器模式 |
| 推理连续失败 | 停止策略并撤销运动命令 | 输入、模型、CPU 负载和循环状态 |
| 动作 NaN/Inf 或越界 | 立即禁止发布并退出模式 | 触发观测、缩放、模型输出和限幅 |
| 关节方向错误 | 急停，不通过改变整体符号盲目试错 | 单关节索引、轴向和模型顺序 |
| 温度或故障异常 | 停止运动并按硬件流程断电检查 | 对应电机、驱动、线缆和负载 |
| 高频振动 | 立即切回 DAMP 或急停 | PD、控制周期、延迟、零位和机械状态 |

当前示例框架没有完整实现状态超时自动停机、关节限位和连续失败阈值。自研算法在实机投入前应明确补齐这些策略，或确认控制器侧已有对应保护并完成实际触发测试。

## 最终验收清单

- [ ] 算法和机器人关节顺序有逐项映射表。
- [ ] 观测每一段的单位、坐标系、缩放和裁剪已记录。
- [ ] 动作语义、缩放、默认姿态和 PD 参数来自同一训练/部署配置。
- [ ] wave、零动作、单关节和单速度轴验证全部通过。
- [ ] 状态中断、模型异常和算法退出的结果已实际测试。
- [ ] 原始关节温度、故障和驱动状态纳入监控。
- [ ] 实机使用保守独立配置，并有支架和急停。
- [ ] 正常退出后控制器不再处于 DEVELOPMENT。
