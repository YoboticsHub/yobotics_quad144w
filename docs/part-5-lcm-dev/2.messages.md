# 5.2 16 维消息协议

Y20W 有 12 个腿关节和 4 个轮关节。算法通常使用每条腿连续排列的 16 维向量，LCM 协议则将其拆成 12 维主数组和 4 维 supplement 数组。

## 关节索引

算法使用以下交错顺序：

| 算法索引 | 腿 | 关节 | 主数组索引 | supplement 索引 |
| ---: | --- | --- | ---: | ---: |
| 0 | LF | hip | 0 | - |
| 1 | LF | thigh | 1 | - |
| 2 | LF | calf | 2 | - |
| 3 | LF | wheel | - | 0 |
| 4 | RF | hip | 3 | - |
| 5 | RF | thigh | 4 | - |
| 6 | RF | calf | 5 | - |
| 7 | RF | wheel | - | 1 |
| 8 | LR | hip | 6 | - |
| 9 | LR | thigh | 7 | - |
| 10 | LR | calf | 8 | - |
| 11 | LR | wheel | - | 2 |
| 12 | RR | hip | 9 | - |
| 13 | RR | thigh | 10 | - |
| 14 | RR | calf | 11 | - |
| 15 | RR | wheel | - | 3 |

```text
算法 16 维:
[LF_hip, LF_thigh, LF_calf, LF_wheel,
 RF_hip, RF_thigh, RF_calf, RF_wheel,
 LR_hip, LR_thigh, LR_calf, LR_wheel,
 RR_hip, RR_thigh, RR_calf, RR_wheel]

LCM 主数组:
[LF_hip, LF_thigh, LF_calf,
 RF_hip, RF_thigh, RF_calf,
 LR_hip, LR_thigh, LR_calf,
 RR_hip, RR_thigh, RR_calf]

LCM supplement:
[LF_wheel, RF_wheel, LR_wheel, RR_wheel]
```

!!! danger "两种 16 维排列不能直接互换"
    算法向量是每腿四项交错排列；LCM 消息在序列化时是 12 项主数组加 4 项 supplement。即使长度都为 16，顺序错误仍会把轮关节命令发送到腿关节。

## `development_state_t`

控制器通过 `Y20W_development_state` 发布：

| 字段 | 类型/长度 | 含义 |
| --- | --- | --- |
| `robot_id` | `string` | 发布状态的机器人标识，当前应为 `Y20W` |
| `joint_q` | `float[12]` | 12 个腿关节位置 |
| `joint_q_supplement` | `float[4]` | 4 个轮关节位置 |
| `joint_qd` | `float[12]` | 12 个腿关节速度 |
| `joint_qd_supplement` | `float[4]` | 4 个轮关节速度 |
| `joint_tau` | `float[12]` | 12 个腿关节扭矩 |
| `joint_tau_supplement` | `float[4]` | 4 个轮关节扭矩 |
| `quat` | `float[4]` | 机身四元数，walk 示例按 `[w, x, y, z]` 使用 |
| `rpy` | `float[3]` | roll、pitch、yaw |
| `omega` | `float[3]` | 机身角速度 |
| `acc` | `float[3]` | 机身加速度 |
| `v_des` | `float[3]` | 期望线速度，walk 使用前两项 |
| `omega_des` | `float[3]` | 期望角速度，walk 使用 z 分量 |
| `mode` | `int32_t` | 控制器当前模式编号 |

`development_state_t` 不包含温度、关节故障、腿使能标志或 SPI 驱动状态。需要这些信息时，另行订阅 `Y20W_QUAD_JOINT_STATE` 的 `quad_joint_state_t`。

## `development_command_t`

外部算法通过 `Y20W_development_command` 发布：

| 字段 | 类型/长度 | 含义 |
| --- | --- | --- |
| `robot_id` | `string` | 目标机器人标识，必须为 `Y20W` |
| `enable_development_mode` | `int32_t` | `1` 请求启用，`0` 请求结束并清零命令 |
| `joint_des_q` / `_supplement` | `float[12]` / `float[4]` | 期望位置 |
| `joint_des_qd` / `_supplement` | `float[12]` / `float[4]` | 期望速度 |
| `joint_des_tau` / `_supplement` | `float[12]` / `float[4]` | 前馈期望扭矩 |
| `joint_des_kp` / `_supplement` | `float[12]` / `float[4]` | 位置误差增益 |
| `joint_des_kd` / `_supplement` | `float[12]` / `float[4]` | 速度误差增益 |

典型执行器目标可理解为：

```text
tau_cmd = tau_des + kp * (q_des - q) + kd * (qd_des - qd)
```

该表达式用于理解字段角色，最终限幅和执行行为由控制器与驱动实现决定。轮关节常用于速度控制，但协议仍同时提供位置、速度、扭矩、Kp 和 Kd；必须按当前控制策略设置，不能仅凭 `wheel` 名称猜测单位或模式。

## 原始关节状态

`quad_joint_state_t` 除 12+4 位置、速度和扭矩外，还包含：

| 字段 | 含义 |
| --- | --- |
| `flags[4]` | 每条腿的状态标志 |
| `spi_driver_status` | SPI 驱动整体状态 |
| `joint_fault[12]` / `_supplement[4]` | 腿关节与轮关节故障 |
| `joint_temp[12]` / `_supplement[4]` | 腿关节与轮关节温度 |

实机安全监控应同时查看 DEVELOPMENT 状态和原始关节状态。只订阅 development 状态无法判断温度与驱动故障。

## Python 重组示例

```python
def interleave_y20w(main, wheel):
    values = []
    for leg in range(4):
        base = leg * 3
        values.extend(main[base:base + 3])
        values.append(wheel[leg])
    return values

dof_q = interleave_y20w(msg.joint_q, msg.joint_q_supplement)
dof_qd = interleave_y20w(msg.joint_qd, msg.joint_qd_supplement)
assert len(dof_q) == 16
assert len(dof_qd) == 16
```

使用项目封装发送交错 16 维命令：

```python
command = {
    "enable_development_mode": True,
    "joint_positions": q_des_16,
    "joint_velocities": qd_des_16,
    "joint_torques": tau_des_16,
    "joint_kp": kp_16,
    "joint_kd": kd_16,
}

with algorithm.latest_command_lock:
    algorithm.latest_command = command
```

`LCMInterface.send_command()` 会把长度正好为 16 的输入按每腿四项拆分。也可以显式传入 12 维主数组和对应的 `*_supplement` 参数。

## C++ 重组示例

```cpp
#include <array>

std::array<float, 16> interleaveY20W(
    const float main_joint[12], const float wheel[4]) {
  std::array<float, 16> result{};
  for (int leg = 0; leg < 4; ++leg) {
    result[leg * 4 + 0] = main_joint[leg * 3 + 0];
    result[leg * 4 + 1] = main_joint[leg * 3 + 1];
    result[leg * 4 + 2] = main_joint[leg * 3 + 2];
    result[leg * 4 + 3] = wheel[leg];
  }
  return result;
}
```

发布 C++ 消息时应逐字段填充 `joint_des_q` 和 `joint_des_q_supplement`，速度、扭矩、Kp、Kd 使用同样的拆分方法，并将 `robot_id` 设置为 `Y20W`。

## `LCMInterface` 输入规则

| 输入形式 | 解释 |
| --- | --- |
| `None` | 主数组和 supplement 全部清零 |
| 少于 12 项 | 已提供的主数组值保留，其余主数组和 supplement 补零 |
| 12 项 | 12 个主关节，4 个轮关节补零 |
| 正好 16 项 | 按四个 `[hip, thigh, calf, wheel]` 腿块解释 |
| 大于 16 项 | 前 12 项作为主数组，随后 4 项作为 supplement，多余项忽略 |
| `{"LF": [...], ...}` | 按 LF、RF、LR、RR 读取，每腿第 4 项作为 wheel |
| 显式 `*_supplement` | 覆盖自动拆分出的轮关节值，不足 4 项补零 |

为避免“长度正确但语义错误”，自定义算法应固定使用交错 16 维形式，或始终显式传入 12+4 两组数据，不要混用。

## 类型生成与兼容

根目录 `.lcm` 文件修改后执行：

```bash
bash scripts/generate_lcm_types.sh
```

LCM 类型哈希与字段名称、类型、长度和顺序相关。协议变化后必须同步：

1. 控制器使用的生成类型；
2. `yobotics_sdk` 中的生成类型；
3. Python 外部算法导入的类型；
4. Viewer 和监控工具；
5. 跨机器运行的另一端。

只有字段数量相同并不代表兼容。看到通道但解码报错时，优先检查是否混用了旧生成文件。

## 验收清单

- [ ] 16 维算法顺序逐项核对，不只检查长度。
- [ ] 四个 wheel 正确进入 supplement 索引 0 至 3。
- [ ] `robot_id` 为 `Y20W`。
- [ ] 位置、速度、扭矩、Kp、Kd 均按相同顺序拆分。
- [ ] 温度和故障从原始关节状态读取，不误认为 development 状态字段。
- [ ] 所有通信进程使用同一版 LCM 类型。

完成协议核对后，再进入 [DEVELOPMENT 模式](3.development-mode.md)。
