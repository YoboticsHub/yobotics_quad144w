# 6.1 Service Architecture

`WebRTC_server/` captures video on the robot side, streams it to clients through WebRTC, and converts DataChannel JSON into Y20W high-level LCM commands.

```text
remote client
  | WebSocket signaling (8765)
  | WebRTC video + DataChannel
  v
signaling_server.py + publisher.py
                   |
                   +--> QUAD_ROBOT_CONTROL_Y20W
                   <-- QUAD_ROBOT_STATE_Y20W
```

- `control_publisher.py`: recommended entry, manages signaling and publisher processes.
- `signaling_server.py`: listens on `0.0.0.0:8765`.
- `publisher.py`: camera, WebRTC, DataChannel, and LCM.
- `config.json`: video, bitrate, LCM channels, and signaling address.

WebRTC is a remote transport layer and does not bypass controller safety checks. Client commands are still handled by the Y20W state machine.

## Process Lifecycle

`control_publisher.py` starts the signaling service first, waits for port `8765` to be ready, then waits for an external client connection. The publisher starts only after the external client creates the ready marker. When signaling disconnects, publisher exits, or PeerConnection fails, components request the manager to restart through `restart.flag`.

```text
control_publisher.py
  +-- signaling_server.py :8765
  |      +-- waits for external client
  |      +-- forwards Offer / Answer
  +-- publisher.py
         +-- reads USB / RTSP / virtual video
         +-- creates WebRTC Offer and DataChannel
         +-- publishes LCM commands and subscribes state
```

## Boundaries

- The signaling WebSocket only forwards session descriptions; it does not carry video frames.
- DataChannel JSON is converted to high-level `sport_client_cmd_t`.
- The publisher always sets `rc_enable=1` and does not manage the full mode lifecycle for the client.
- The current forwarding layer only converts types and does not limit motion ranges.
- Control safety must still be guaranteed by the client, controller state machine, and onsite emergency stop together.
