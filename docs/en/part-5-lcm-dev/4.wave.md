# 5.4 wave Rule Example

`wave_algorithm` does not load an ONNX model. It directly generates low-frequency sinusoidal joint offsets. It covers state reception, 16D layout, command caching, high-frequency sending, and safe exit, making it the preferred first example for understanding the DEVELOPMENT link.

## Use Cases

- First validation of the external-algorithm environment and LCM channels.
- Checking 12+4 joint mapping and four-leg directions.
- Verifying PD parameters and command send frequency.
- Establishing a minimal project template for custom rule algorithms.

It is not a gait controller. The default motion only applies periodic offsets to thigh and calf. It does not provide balance, foothold planning, or disturbance rejection.

## Startup Prerequisites

1. Python can import `numpy`, `yaml`, and `lcm`.
2. MuJoCo and the controller are already running.
3. `Y20W_development_state` updates continuously.
4. The robot is in a state that can safely switch modes.
5. For hardware tests, the robot is on a stand and emergency stop is ready.

Run from the project root:

```bash
python3 external_algorithms/wave_algorithm/run_algorithm.py   --config external_algorithms/wave_algorithm/config.yaml
```

You can also run from the algorithm directory:

```bash
cd external_algorithms/wave_algorithm
python3 run_algorithm.py --config config.yaml
```

## Configuration Sections

### `policy`

| Field | Default | Purpose |
| --- | --- | --- |
| `type` | `none` | Rule algorithm; no actor or encoder is loaded |
| `model_path` | empty | Not used by wave |
| `encoder_path` | empty | Not used by wave |
| `read_metadata` | `false` | No model metadata |
| `warmup_count` | `0` | Skips ONNX warmup |
| `action_threshold` | `200.0` | Base warmup threshold; inactive because there is no warmup |

`RunAlgorithm._load_policy()` sets `model` and `encoder` to `None` and marks the policy type as `none`.

### `model_params`

| Field | Default summary | Purpose |
| --- | --- | --- |
| `num_actions` | `16` | Per-leg `[hip, thigh, calf, wheel]` |
| `num_obs` | `57` | Observation buffer length retained for base-class reuse |
| `default_joint_pos` | Per leg `[0, -0.8, 1.6, 0]` | Reference posture before sinusoidal offsets |
| `joint_stiffness` | Leg joints `8`, wheels `0` | Position gain Kp |
| `joint_damping` | Leg joints `0.2`, wheels `0.5` | Velocity gain Kd |
| `action_scale` | All `1.0` | Current wave implementation does not apply this field again |

!!! note
    `process_action()` directly computes `default_joint_pos + action`. The wave amplitude is added directly to target joint position, and `action_scale` is not used in the current implementation.

### `lcm`

| Field | Default | Purpose |
| --- | --- | --- |
| `url` | empty | Use default LCM configuration |
| `state_channel` | `Y20W_development_state` | Receive DEVELOPMENT state |
| `command_channel` | `Y20W_development_command` | Publish DEVELOPMENT commands |
| `robot_id` | `Y20W` | Filter state and mark the target robot |

### `execution`

| Field | Default | Purpose |
| --- | ---: | --- |
| `frequency` | `100.0 Hz` | Sinusoidal action update frequency |
| `lcm_send_frequency` | `200.0 Hz` | Send frequency for the latest command |
| `auto_start` | `true` | Locally starts after matching state is received |
| `auto_end` | `true` | Calls the end flow when maximum runtime is reached |
| `max_execution_time` | `0.0 s` | No time-based auto stop |

### `motion`

| Field | Default | Purpose |
| --- | ---: | --- |
| `frequency` | `0.1 Hz` | Sinusoidal motion frequency; one cycle is about 10 seconds |
| `amplitude` | `0.5` | Thigh peak offset; calf peak offset is twice this value and opposite in sign |

Other configuration:

- `rl_mode.is_rl_mode: false` marks this as a rule-control example.
- `joint_mapping.enabled: false`; the example uses fixed Y20W order.
- `debug.print_config: true` prints the final configuration at startup.
- `debug.print_metadata: false`; there is no ONNX metadata.

## Action Generation

For runtime `t`, frequency `f`, and amplitude `A`:

```text
phase        = 2 * pi * f * t
thigh_offset = A * sin(phase)
calf_offset  = -2 * A * sin(phase)
```

Each leg receives:

```text
[hip, thigh, calf, wheel]
  = [0, thigh_offset, calf_offset, 0]
```

All four legs use the same phase, so the visible motion is mainly synchronized body height change:

- hip adds no lateral swing;
- thigh and calf move in opposite directions, approximately keeping the foot horizontal;
- wheel offset remains zero to avoid turning the communication test into wheel motion.

`process_action()` then builds:

```text
q_des   = default_joint_pos + action
qd_des  = 0
tau_des = 0
kp/kd   = arrays from model_params
```

The interleaved 16D array is split by `LCMInterface` into 12 leg joints and 4 wheel supplements.

## Method Roles

| Method | Role in wave |
| --- | --- |
| `compute_observation()` | Recombines 12+4 position and velocity into the first 32 observation values, with velocity command and quaternion for debugging |
| `_run_inference()` | Ignores observation content and generates a 16D sinusoidal action from time |
| `process_action()` | Checks action length, adds the default posture, and updates the command cache |
| `on_development_mode_start()` | Resets start time and step count so the sine wave starts from a new cycle |
| `on_development_mode_end()` | Sets the latest command to `enable_development_mode: false` |

`compute_observation()` catches field-access exceptions internally. When a field is abnormal, the corresponding region may remain zero. This is useful for demonstration but should not be treated as strict state-integrity validation.

## MuJoCo Validation Flow

1. Start simulation:

```bash
bash scripts/start_mujoco.sh
```

Confirm the model appears stably and the controller has no configuration or model-loading errors.

2. Monitor channels:

```bash
bash scripts/monitor_lcm.sh --no-gui
```

Confirm `Y20W_development_state` first; do not depend on wave commands yet.

3. Start wave:

```bash
python3 external_algorithms/wave_algorithm/run_algorithm.py   --config external_algorithms/wave_algorithm/config.yaml
```

Successful logs should include the config path, `policy.type='none'`, inference frequency, send frequency, and DEVELOPMENT startup message.

4. Enter DEVELOPMENT using the current gamepad or host-control method. Confirm the state `mode` changes; do not rely only on algorithm logs.

5. Check motion:

- Four legs move in the same direction pattern.
- hip and wheel have no obvious periodic targets.
- thigh and calf move in opposite directions.
- Commands are continuous with no instant jumps.
- The observed period is close to `motion.frequency`.
- `Y20W_development_command` frequency is close to the configured `200 Hz` range.

6. Exit by switching back to DAMP before pressing `Ctrl+C` to stop the algorithm. Confirm `enable_development_mode` becomes `0` and the robot is not left in DEVELOPMENT.

## Conservative Tuning

Do not use the simulation amplitude directly for the first hardware test. Use a separate configuration copy and tune in this order:

1. Keep low frequency and reduce only `amplitude`.
2. Verify four-leg direction and zero positions.
3. Adjust `frequency` only after amplitude is fixed.
4. Check Kp and Kd last according to response.
5. Change only one parameter group each time and record the result.

`calf_offset` is `-2 * amplitude`, so calf peak offset is larger than thigh. Judge safe amplitude by calf peak, not only by the configured `amplitude`.

## Troubleshooting

| Symptom | Check | Possible cause | Handling |
| --- | --- | --- | --- |
| Algorithm starts but no motion | State channel, `robot_id`, control mode | No state received or not in DEVELOPMENT | Check [Mode Lifecycle](3.development-mode.md) stage by stage |
| Only some legs move | 16D order and 12+4 message | Array length, leg order, or generated type error | Check indices leg by leg with low amplitude |
| Leg direction differs from expectation | URDF/XML axis and default posture | Different joint sign convention | Verify one joint in simulation before increasing amplitude |
| High-frequency vibration | Kp/Kd, frequency, state delay | Gains too high or link jitter | Exit immediately, then reduce gains and amplitude |
| Jump on switching | Current posture vs. `default_joint_pos` | Target jumps from actual position to default posture | Align posture before entry or add interpolation in custom code |
| wheel moves unexpectedly | supplement order and wheel target | 16D interpreted as first 12 plus last 4 | Check interleaved mapping and supplement |
| Still in DEVELOPMENT after `Ctrl+C` | Controller state and disable command | Process was killed or state machine did not switch back | Use a safe control entry to switch to DAMP, then disconnect |

## Pass Criteria

- wave runs for multiple cycles with no NaN, exception logs, or long frequency drops.
- Four-leg joint direction, wheel supplement, and default posture are all correct.
- State changes from entering to exiting DEVELOPMENT are repeatable.
- After algorithm exit, the robot is in a safe mode.
- Only after the above pass should you validate the [ONNX Walking Example](5.walk-onnx.md).
